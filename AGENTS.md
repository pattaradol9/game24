# Agent Guidelines

## Language policy

- Communicate with the user in **Thai**: conversation, explanations, summaries, and questions.
- Everything that gets implemented must be in **English**: code identifiers, code comments, commit messages, documentation (README, ADRs, API docs), `.env.example` descriptions, test names, and log/error messages.
- Exception: user-facing product UI copy in `web/` stays bilingual (Thai/English) by design — do not translate it as part of this policy.

## Terminal policy

- Never leave background processes running when the work is done. Stop every dev server, watcher, or long-running command you started (verify the ports are actually free — `go run` children can outlive their wrapper).
- The user runs and verifies the app themselves (e.g. `make dev`). Do not keep servers up "for convenience"; closing the terminal after finishing is mandatory, every time.

# Game Systems

Documentation for the meta-game systems layered on top of the core 24-gameplay: coins, achievements and card skins. All persistence is server-side in SQLite (`store` package); the web client never owns balances.

## Scoring & levels

- **Hand score vs EXP**: a solved solo hand mints two deliberately different curves. **Score** = `progress.ScoreForHand((10 + remaining seconds) × mode multiplier, level)` — speed-heavy, times the solver's **level handicap** (`progress.ScoreMultiplier` = `1 + 0.05 × (level − 1)`, Lv.1 ×1.00 → Lv.100 ×5.95); it is the scoreboard figure (`rounds.points`, the submit response's `points`, the solo session tally). **EXP** = `progress.ExpForHand(remaining, mode multiplier)` = `round((8 + remaining/2) × modeMult)` — a solid base for solving, speed at half weight, mode-scaled, and NOT level-multiplied (levels must not compound progression); it is the payout base (`store.AwardSolve` banks it, boost multipliers stack on top, `store.CoinsForHand` pays coins off it 10:1). Timeouts/skips pay zero of both.
- **Level cap**: the ladder ends at `progress.MaxLevel` (100 — the top of the tier table and the level-100 "Master of 24" achievement). EXP past the cap still banks and shows on the bar, but `LevelFromExp` never returns more than 100 and `LevelProgress` reports `expForNext` 0 at the cap, so `XpBar` renders full with a `MAX` count. The client mirrors all of it in `web/src/core/progress.js` (`MAX_LEVEL`, `levelFromExp`, `levelProgress`, `scoreMultiplier`) — the two ladders are pinned by tests on both sides.
- **Solo difficulty ladder**: a solo run never sits still. Every **10 hands dealt** (`game.LadderStepRounds`) climbs one rung: the puzzle steps up one mode from the run's starting pick (jack → queen → king → ace, ace caps the walk) and the countdown shrinks **10% per rung** off the run's base window, flooring at **30 seconds** (`game.LadderMinTimeSec`) — the hardest state the ladder can reach ("H": ace puzzles on the minimum clock; a run reaches the floor after 140 dealt hands from jack, 110 from queen, 90 from king, 70 from ace). The rung is resolved server-side in `game.LadderConfig`: `createRound` takes the client's `stage` (clamped to 0–40), deals the rung's mode, stamps the hand's own window on the `rounds.time_limit` column (0 = the mode default), and answers `mode`/`stage`/`timeLimit`; the submit expiry fence, the remaining-time payout, the timeout eligibility and the extend echo all judge the hand by its stamped window (`roundBaseWindow` in `api.go`), never the mode default. The EXP/coin multiplier and the dealt number range follow the resolved mode, so per-mode stats and leaderboards stay intact. The client places the rung only: `useGame` keeps the run's ladder state (`runMode`, `handNo`, `runBaseTime`, mirrored in the refresh snapshot alongside the session, resetting with the tallies on a game-over), sends `ladderStageFor(handNo)` with each deal and adopts the server's resolved mode/window; the `ModeBadge` reads "รอบที่ N · −P%" (drop vs the run's base window, capped by the 30s floor) and each climbed rung toasts once — mode step (`ladderUp`), time-only drop (`ladderTime`), or the floor (`ladderFloor`) — off the `ladderStep` event. Helpers math is unchanged: Add-time still clamps to the hand's own (now shrunken) window.
- **Game session & summary**: the solo run is one *game*: solved hands chain, banking their `+points`/`+exp`/`+coins` into the `sessionScore`/`sessionExp`/`sessionCoins` tallies in `useGame.js` (the bank happens in `submitWin` before the snapshot save, so a refresh on the dialog keeps them), until the clock beats the player — the timeout dialog then carries a **game summary** block (the run's score/EXP/coin totals, `ResultModal` props), and starting over resets the tallies. The side panel's score section shows the bare live tallies — the score headline plus compact banked EXP/coin rows, hidden while zero and for guests (no level, no multiplier); the win dialog carries no payout figures and no profile at all — the summary block, the **profile + level bar** (moved out of the win dialog) and the level-multiplier chip on the score row live only in the game-over dialogs.
- **Leaving the game**: the solo Exit button confirms first (`ConfirmModal.vue`) — ending the game freezes the clock, shows the same summary dialog with an "exit game" action, then routes home. A same-tab **refresh resumes the game exactly where it stood**: `useGame` mirrors the live session (round id, board state incl. selection, tallies, hint/extend/skip quotas, absolute deadline, and the ladder's `runMode`/`handNo`/base window) into `sessionStorage` and replays it on mount with no countdown, reusing the stored session id so the server-side quotas treat the reload as one continuing visit; refreshing on a result dialog banks the tallies (win) or wipes them (game-over) and deals the next hand (the ladder chaining forward on a win, restarting on a game-over). Closing the tab still ends the session with nothing further banked, which is safe by construction — the server only banks verified submits inside a hand's own window, so an abandoned open round can never pay and the snapshot cannot stretch any window.
- **Helper buttons**: the solo action row is the helper group — **Solution** (the hint endpoint; label reuses the `solution` key), **Add-time** and **Skip**. The group shows no remaining counts anywhere: availability is communicated by the disabled state alone. A dark helper explains itself where it stands — hovering shows the reason tooltip, and pressing a dark helper (a transparent gate over the disabled button catches the click) pops a bubble over the button naming why: no item in the bag (`timeNeedsItem` / `skipNeedsItem`), this visit's quota already spent (`timeExtendOnce` / `skipSpent` / `hintsSpent`), or the clock already full (`timeFullLimit`). The pop is animated by a dedicated `why-pop` keyframe that restates the bubble's centering transform (a bare `rise-in` strips `translateX(-50%)` mid-animation and the bubble jumps sideways), and each press plays a golden spark burst through `web/src/three/popupFx.js` — ONE shared full-viewport canvas for the whole app, booted lazily on the first press, asleep (no rAF) between bursts, DOM-pixel-space orthographic scene with launch math pinned by `three/popupFx.test.mjs`, following the GameBackdrop discipline (dynamic import, qualityGuard, reduced motion never boots it, full dispose on unmount).

## Multiplayer rooms

- **Every seat plays the round; the round ends with the last solver**: on submit a correct trace banks the seat's OWN time-based points — `(10 + seconds remaining on its clock) × mode multiplier` — into its room score, counts a `win`, and flags the seat solved for the round (`player.solvedRoundNo` + the finish order `player.solveOrder`, stamped from the room's per-round `solvedCount`; exposed in every `room_state` as `solved` / `solveOrder`). **The board never collapses**: a done seat (solved, or its own clock ran out) and the round summary keep the GameBoard's exact footprint and blur the cards under a status veil — ตอบเสร็จแล้ว!/หมดเวลา! plus the waiting copy during the round, blur-only behind the summary dialog — instead of swapping in a smaller panel; `PlayersRail` swaps the done seat's score cell for a ตอบเสร็จ #N/Solved #N tag carrying the finish order (หมดเวลา/Time out when the clock beat it). The steps strip stays through the summary too, so the column never jumps. **Private clocks die at different times**: `Room.settleRoundLocked` flags every unsolved seat whose own clock (shared deadline or its live extension) has passed as `timedOutRoundNo` / roster `timedOut` — shown as a หมดเวลา/Time out tag and a "clock ran out, waiting for the others" panel — and a seat is DONE once it has solved or timed out. The round closes the moment the LAST seat is done (`Room.allDoneLocked`, checked in `Submit` and in each `expire` fire, which reschedules itself to `nextDeadlineLocked` — the earliest still-live clock; a done seat's extension never holds the round open). `round_result` carries `{roundNo, solution, standings}` where each standings row adds `gained` (this round's points), `solved`, `solveOrder` and `timedOut`; the canonical solution is always included. Seats that are done cannot submit, hint, regen or extend again that round, and their clock display goes quiet — no countdown beats or urgency vignette on a clock that no longer matters. `viewLocked` guards solved/timedOut with `roundNo > 0` — the lobby (round 0) must never flag anyone.
- **The host gates every transition — with a stall guard**: rounds never advance instantly on their own. In the summary, the host's `Room.Next` (ws `next` message) starts the next round, and after the last round the same call closes the match into the podium; members see a "waiting for the host" line. To keep a silent host from freezing the room, every summary also arms `scheduleAutoNext` — a 60-second window (`autoNextDelay`) after which `autoAdvance` moves the match on by itself (next round, or the podium). The `round_result` payload carries `autoNextAt` (epoch ms) and `RoundSummary.vue` renders the live countdown on the host's continue button (a seconds pill; members get it as a text line instead); both paths funnel through `advanceLocked`, whose under-lock state re-check makes a host press racing the timer move the match exactly once.
- **The host's goodbye ends the match with a podium**: the client sends an explicit `leave` ws message only on a confirmed Exit (a refresh or a dropped socket never does, so the reconnect grace stays intact). When the host seat's `leave` lands, `Room.HostLeft` seals the room at once and the hub drops it — a match still standing freezes into a final `match_end` whose `standings` now carry a 1-based `rank` plus `reason: "host_left"`, so every seat still connected gets the `FinalPodium` with a "host left" note (`hostLeftNote`) before heading home; a bare lobby (round 0) gets the plain `room_closed`. The same podium goodbye plays when the host's reconnect grace expires with no return — `Room.Shutdown` runs through the same `endByHostLeftLocked` teardown (broadcast + a 100 ms flush beat, then every connection is cut). The host's own confirmed exit stays on the page for the incoming podium (a 2.5 s dead-socket fallback routes home); the client cuts its own socket on a `host_left` `match_end` (the room no longer exists server-side) and ignores `room_closed` once the podium is up. Member goodbyes keep the warm-seat flow untouched.
- **The room summary animates the ledger**: `RoundSummary.vue` lists the WHOLE roster ranked by THIS round's result — `gained` descending (cumulative score breaks ties), each row wearing its place badge (gold/silver/bronze for the podium) — with avatar, name, a ตอบเสร็จ/ไม่ทัน status, the round's `+gained` chip (muted +0 for misses), the cumulative score ticking up with an eased, staggered rAF count from `score − gained` (the previous total, 0 in round one) to the new total, and the host's continue button (รอบต่อไป, or ดูผลการแข่งขัน after the last round) / the members' waiting line. The win sting and celebration fire when the local seat's `gained > 0`. Every solver banks EXP/coins through the same `store.AwardSolve(roomWin=true)` path (personal item boosts ignored, server boosts applied), so per-solve payouts mirror the per-round points.
- **Rooms cap at 10 seats**: `room.maxPlayers` is enforced on fresh joins (`Room.Join` returns an error → the ws layer replies `error` and the client drops to the closed-room screen); a resume reattach or a host reclaiming its own absent seat never grows the roster, so they are always allowed.
- **The room play page mirrors the solo one**: `RoomGame.vue` renders the room's helper group — **Solution** (the per-match hint quota, dark with the `hintsSpent` bubble once spent), **Add-time** (the per-match extend quota, `extendsSpent` bubble) and **New hand** (`regen`, the per-match regen quota, `regensSpent` bubble) — with the same gate-over-dark-button why-popups and popupFx glint, and no remaining counts anywhere. The steps history lives under the board as a horizontal strip (`StepHistory`'s `horizontal` variant), undo pinned at its far right end; the side panel is the player roster (`PlayersRail`, titled รายชื่อผู้เล่น/Players) with a compact round-progress panel pinned at its bottom (รอบที่ n / total with a progress fill, hidden while the host hasn't started) — no level/EXP box in the room, the `XpBar` stays solo-only. The header carries the `BuffBar` on desktop. Combo pops the board-center text and toast bubbles (`bubbleWin`/`bubbleTime`/`bubbleCombo`/`bubbleWrong`), and leaving mid-round confirms first (`leaveTitle`/`leaveBody`). The room keeps its own non-blocking achievement toast stack (they may land over a round summary) instead of the solo `CelebrationPopup`.
- **Room helpers are room-provided, never personal**: every helper spends a quota the host fixed at room creation (`room.Config` `HintQuota` / `ExtendQuota` / `RegenQuota`, each 0–5, seeded identically into every seat and exposed per player as `hintsLeft` / `extendsLeft` / `regensLeft`). Every helper is additionally capped at **one use per seat per round** — a per-seat round stamp (`hintRoundNo` / `extendRoundNo` / `regenRoundNo`) refuses a second press on the same hand, and the welcome round payload carries `hintUsed` / `extendUsed` / `regenUsed` so a refresh cannot unlock an already-spent helper. Multiplayer never touches the players' item inventory — every seat (guests included) gets exactly the same allowance, so nobody can buy an edge. There is no separate fold-skip in a room: a stuck hand is escaped by spending a regen (เปลี่ยนโจทย์), which swaps in a fresh solvable hand instead of folding.
- **Add-time in a room is private**: the `extend` websocket message spends one seat quota unit and moves the seat's private deadline to the shared deadline + `room.extendSeconds` (30s). The round stays open until the last live private deadline passes (`Room.expire` reschedules itself), every seat submits against its own clock (`Room.Submit` refuses past it and pays remaining-time points off the widened window), and a refresh resumes the widened clock through the welcome round payload (`extendEndsAt`/`extraSeconds`). `extendEndsAt` resets each round; the quota counters persist for the match.

## Coins

- Every **solved hand pays EXP and coins**, in solo play and in multiplayer rooms alike, mirroring how EXP is already awarded.
- Payout formula (`store.CoinsForHand`): `coins = points / 10`, minimum 1 — deterministic, so the client can show the payout from the submit response without extra round trips. Skipped/expired hands pay nothing.
- Balances live in `players.total_coins`. Every multiplayer round solve awards coins through the same path (`store.AwardSolve` with `roomWin=true`, which also increments `total_wins` for win-count achievements).
- **Guests rank on the leaderboard, nothing else**: anonymous players bank their solved hand's score-ledger row only — solo through `store.RecordScore` in the submit handler, room wins through the hub award callback's guest branch (the room seat resolves its dbID even for guests, flagged `Guest` on `room.Info`) — while EXP/coins, per-mode stats and achievements stay gated on `!player.IsGuest`. `ScoreLeaderboard` filters banned players only, so guest rows appear with Lv.1/bronze badges and no streak; a player whose best hand inside the window is 0 (`HAVING MAX(sc.points) > 0`) never appears at all.
- **High scores ride the player JSON**: `player.highScores` maps each played mode to the best single hand there (`store.PlayerHighScores` over the same ledger the leaderboard ranks, positive modes only, omitted while empty). The profile menu (`ProfileMenu.vue`) renders it as a compact per-mode grid under the stats block — shown for every player with a scored hand, guests included, since guests have no level ladder of their own.

## Achievements

- Catalog of exactly **50 achievements** in `internal/achv` (`achv.Catalog`), single source of truth, evaluated server-side only.
- Each entry has an **escalating reward by difficulty tier**: bronze → silver → gold → platinum → legend (e.g. bronze ≈ 20–60 EXP / 15–40 coins, legend ≈ 1200–2000 EXP / 800–1300 coins). Rewards are paid automatically on unlock, in the same transaction that records the unlock.
- Tracked metrics: lifetime solves (total + per mode), best streak, level, coins held, multiplayer round wins, fastest solve (best time in ms, lower-is-better), solves without hints, hints used, distinct play days, skips. Counters derive from `player_mode_stats`, the `rounds` table and `players` columns — the snapshot builder is `store.AchievementSnapshot`.
- **Evaluation points**: after every hand (solved or skipped) in solo play (`store.AwardSolve` / `store.AwardSkip`) and after every multiplayer round win (hub award callback in `cmd/server/main.go`). Newly unlocked entries are returned inline in the REST responses (`newAchievements`) or pushed to the winner over the room websocket (`{type: "achievements", data: {unlocked: [...]}}`).
- Unlocks persist in `player_achievements` (id + timestamp); `store.EvaluateAchievements` is idempotent — already-unlocked entries are never re-granted.

### API surface

- `GET /api/v1/achievements` — public catalog + (with token) `unlocked` map and `progress` map (`{current, target}` per id). Guests get an empty unlocked/progress map.
- Player JSON now includes `totalCoins` and `skin` (equipped skin id, `""` = classic).

## Server boosts

- **Server-wide payout multipliers** the admin authors in advance and arms when the event should start — one campaign per kind: `exp` multiplies the EXP every solved hand banks, `coins` multiplies its coin payout. One row per kind in the `boosts` table (`kind` unique, seeded with disarmed ×2/60min drafts; `store.AllBoosts`). Databases from before the coins kind carried their config over through a migration that renames `exp_boost` → `boosts` (kind `exp`), so an armed window survives the upgrade.
- **Arming**: enable starts the window at now → now + duration (`store.EnableBoost`); enabling an already-active boost restarts the window. Disable stops payouts immediately while keeping the config for the next run (`store.DisableBoost`). An armed window simply expires when `ends_at` passes — nothing to clean up. Config saves (`store.SetBoostConfig`) never touch the run state, so a live boost can be retuned mid-event; the new multiplier applies to subsequent hands, and the running window is untouched.
- **Payout**: while a kind's window is open (`store.ActiveBoost(kind)`, compared against SQLite's clock) every solved hand's payout is multiplied by `BoostAmount(base, multiplier)` = `round(base × multiplier)` — solo play and multiplayer round wins alike (the lookups happen inside `store.awardEXP` via `store.payoutMultiplier`, before the transaction opens: the pool holds a single connection, so querying inside the tx would deadlock). The coin boost multiplies `CoinsForHand`'s output. **Sources stack additively, never compounding**: the server-wide campaign and the player's own item boosts each contribute their bonus (multiplier − 1) to one shared stack — for solo hands — so a ×2 server boost plus a ×2 personal item pays ×3, not ×4 (see Shop items). A multiplayer round win stacks the server campaign only (`payoutMultiplier`'s `personal` flag is false for `roomWin` payouts): room results must stay fair, and the server-wide boost applies to every seat alike. **Achievement rewards are never multiplied**, and guests are untouched by the existing gate.
- **Visibility**: running boosts ride in the player JSON as `boosts: {"exp": {kind, multiplier, endsAt, sources}, "coins": …}` (omitted when nothing runs) — `multiplier` is the additive stack of every source and `sources` names each one (`{origin: "server"|"item", multiplier, endsAt}`), so every profile fetch, ws snapshot and `player` push carries them. The solo submit response additionally returns `exp` — the EXP the hand actually banked — and its `coins` figure is the boosted amount; the result dialogs surface those banked figures only in the game-over summary block (no per-hand payout lines or `×N` chips — the live `BuffBar` is the multiplier's showcase). Players see Ragnarok-style buff icons (`BuffBar.vue`, an inline tray: in the Home header next to the profile/sound/language cluster on desktop, in the solo header, and inside the mobile quick-settings sheet; the mobile header itself collapses sound + language + boosts into one `QuickSettings.vue` gear popover), each cell carrying the stacked multiplier, a live countdown and a tooltip. The client splits the sources into the `serverBoosts`/`itemBoosts` refs in `web/src/auth.js` and re-stacks them per tick (`mergeBoosts`), so an expiring source drops out of the math without a push.
- **Live updates**: every server-wide boost mutation broadcasts a `boost` event (`{"boosts": {…}}` — the full server view, empty when none) to **all** connected player sockets via `presence.Broker.Broadcast`; open tabs swap their buff icons without a refresh. The client applies it to the server half only — personal item boosts never ride the broadcast.

### API surface

- `GET /api/v1/admin/boosts` — every kind's config + run state (`kind`, `multiplier`, `durationMinutes`, `label`, `enabled`, `active`, `startsAt`/`endsAt` RFC3339, `remainingSec`, `updatedBy`/`updatedAt`); `GET /api/v1/admin/boosts/{kind}` — one kind.
- `PUT /api/v1/admin/boosts/{kind}` with `{multiplier, durationMinutes, label}` — saves the draft (×1–×100, 1 min–30 days; out of range → 400 via `store.ErrBoostRange`; unknown kind → 404; label clamped to 80 chars). Events `admin.boost.set` (kind + before/after), `admin.boost.enable` (kind, endsAt), `admin.boost.disable` (kind).
- `POST /api/v1/admin/boosts/{kind}/enable` / `POST /api/v1/admin/boosts/{kind}/disable` — arm/stop one kind; each success responds with the fresh state and fans it out to every open socket.
- Admin portal: the **Server Boosts** tab (`AdminBoosts.vue`) renders one `AdminBoostCard` section per kind — status badge with a live countdown, the draft form (multiplier, duration with unit presets, label), Save settings / Enable now / Disable. The portal header shows a pulsing badge per running boost (polled every 30s and refreshed on every boost mutation), so what's active is visible from any tab.

## Shop items: personal boosts & inventory

The shop (`/shop`, `web/src/views/ShopView.vue`) unifies the card skins and consumable boost items under one page with three tabs — **Card Skins** (the old `/skins` page, now `SkinShopPanel.vue`), **Boost Items** (`ItemsShopPanel.vue`) and **Inventory** (`InventoryPanel.vue`) — plus a shared coin balance in the header; the old `/skins` route redirects. Buying a skin and buying an item are both Google-gated.

- **Catalog**: 10 consumable items in `internal/items` (`items.Catalog`) — eight payout boosts, four per payout kind, tiered by rarity like the card skins — ×2/30min (common: `coin2` 300, `exp2` 400), ×2/60min (rare: `coin2h` 550, `exp2h` 720), ×5/30min (epic: `coin5` 1100, `exp5` 1400), ×10/15min (legend: `coin10` 1900, `exp10` 2400) — plus two play helpers, `time30` "Sand Saver" (common, 150) and `skip1` "Skip Pass" (common, 120). Each def carries kind (`exp`/`coins`/`time`/`skip`), multiplier, duration, price, rarity and a bilingual name/desc that says the server stacking is additive; play-helper items (`time`/`skip`) never arm a boost window — time items carry `extraSeconds` (seconds one unit adds to a hand), skip items fold one hand.
- **Time extension in play**: the solo action row carries a dedicated **Add-time** button (it took Undo's slot; Undo moved into the Steps panel header, `StepHistory.vue` emits `undo`) that spends one `time30` any time mid-play — no need to wait for the countdown to die. A hand's remaining time may **never pass the mode's base window** (`game.Config` `TimeLimitSec`; e.g. a Jack hand pressed at 1:50 remaining tops up to 2:00, not 2:20): `POST /rounds/{id}/extend` → `store.ExtendRound` consumes ONE unit and stamps `rounds.extend_sec` clamped to the seconds the hand has already played away on the server clock (a press with no room at all refuses with `ErrRoundTimeFull` → 400, nothing consumed) in one transaction; the once-per-session rule (one extension per client-generated `sessionId`, mirroring the hint quota) is enforced in the same transaction — any round of the session already carrying `extend_sec > 0` refuses a second (`ErrSessionExtendUsed` → 400). The client mirrors the clamp (`useGame.addTime` tops `remaining` out at the base `timeLimit`), disables the button while the clock is full, and toasts the seconds actually gained. The zero-time bailout stays: a hand that reaches 0:00 with the quota still unspent and the bag non-empty parks on 0:00 and raises `TimeExtendModal.vue` ("spend one unit for +30s?"); declining (or a refused extend) falls through to the plain timeout flow (free fold via `POST /rounds/{id}/timeout`). The widened window counts everywhere: `submitRound` compares elapsed against `timeLimit + extend_sec + 10` and pays remaining-time points off the widened limit, so the extra seconds are genuinely playable. Events `item.use` with the round/session detail; the extend response echoes `{roundId, timeLimit (base+extra), extraSeconds, player}`.
- **Skip gating in play**: the solo Skip button is item-gated — folding a hand mid-play costs one `skip1` unit and only one fold per play session is allowed. `useGame.skip` refuses to fire for guests, empty bags or an already-spent session (`skipUsed` ref, session-scoped and refresh-proof via the snapshot, like `extendUsed`); `SoloGame`'s button goes dark with a `skipNeedsItem` tooltip when unavailable (the helper group shows no remaining counts). The press calls `POST /rounds/{id}/skip` → `store.SkipRound` consumes ONE unit, stamps `rounds.skip_used` and finishes the round as "skipped" in one transaction; any round of the session already carrying `skip_used > 0` refuses a second (`ErrSessionSkipUsed` → 400). Payout stays zero either way and skip achievements still evaluate. A hand that merely times out folds FREE through `POST /rounds/{id}/timeout` — the handler verifies the expiry server-side against `dealt_at + timeLimit + extend_sec`, so it can never stand in for a mid-play skip (the submit path keeps its own extra +10s grace). Both endpoints respond `{solution, newAchievements, player}` (the skip also pushes `player` over the ws since the bag changed); timeout on a live hand → 400, on a closed round → 409.
- **Inventory**: `player_items` holds one stacked qty per item (`store.PlayerItems`); spending the last unit deletes the row. The player JSON carries `items: [{id, qty}]` (omitted for guests), so every profile fetch, ws snapshot and `player` push doubles as an inventory sync.
- **Buying**: `store.BuyItem(playerID, itemID, count)` debits price×count and upserts the stack in one transaction, so a batch is all-or-nothing — a player either affords every unit or spends nothing; guests → 403, unknown item → 404, not enough coins for the whole batch → 400 (`ErrInsufficientCoins`), count outside 1–200 → 400 (`ErrInvalidCount`), event `item.buy`. The inventory dialog offers a count slider from 1 to what the balance affords (floor(balance ÷ price), capped at the same 200 bound). Items are consumable, so the shop CTA never turns into an "owned" state — the card shows the stack size instead.
- **Using — N units at once, one window per kind**: `store.UseItem(playerID, itemID, count)` consumes `count` units — every unit contributes its own duration — and moves the kind's single window in `player_boosts` (multiplier + `ends_at` + `item_id`). What happens depends on what is live: **same kind + same multiplier stacks TIME** (×2/30min + ×2/60min = ×2 for 90min — durations add onto the live end), **same kind + different multiplier REPLACES** the live window (fresh start from now, new multiplier), **nothing live** starts fresh. The window may never run past `store.BoostWindowMax` (24h from now): a use that only PARTLY fits is **clamped at the cap** — time beyond it is trimmed, the response flags `capped: true`, and the units are still consumed; only a window already sitting at/past the cap gains nothing and is refused with `ErrBoostDurationCap` (HTTP 400 "boost duration cap exceeded (24h)"), rolling the transaction back so nothing is consumed. The inventory dialog mirrors the math up front: it derives how many more units still fit under the cap (room ÷ item duration, **rounded up** — 7.5 fits → 8, the overhang trimmed server-side) and offers a count slider from 1 to that ceiling, disabled entirely at zero room. Boosts of DIFFERENT kinds (EXP + coins) and the server-wide campaigns always run alongside and stack additively. The use response's `action` field (`fresh` | `extended` | `replaced`) tells what happened, plus echoed `count` and `capped`. Events `item.use`; guests → 403, empty/short stack → 400 (`ErrNoItems`), count outside 1–200 → 400. Windows simply expire when `ends_at` passes.
- **Payout**: personal boosts enter the same additive stack as the server-wide campaigns (see Server boosts → Payout) — `store.payoutMultiplier` sums every source's bonus on top of the base, applied to solo solves only; multiplayer round wins ignore the personal half of the stack (room payouts keep every seat equal), while the server-wide campaigns still multiply them.
- **Visibility & live updates**: the player JSON's `boosts[kind].sources` distinguishes `server` from `item` origins and `boosts[kind].multiplier` is the combined stack, so the `BuffBar`/`BoostsMenu` trays show the true payout; item sources carry `item`, bilingual `name` and `rarity`. The tray cells are terse (icon + stacked ×N + compact countdown via `web/src/duration.js`: `24h` → `59m` → `59s`) and hover/focus opens a popup with the per-source breakdown. Colour is the pedigree: pure server-wide cells wear the reserved server teal (`#29d3be`, never used by rarities), item-fed cells wear the highest rarity among their items (common dark green (`--rarity-common`) → rare blue → epic purple → legend gold). Buy and use both respond with the fresh player JSON and push a `player` snapshot over the player socket, so open tabs pick up new counts and buff icons without a refresh; the `boost` broadcast stays server-only.
- **Ambience**: every shop tab mounts `FxBackdrop.vue` — ONE shared WebGL canvas per tab (`variant` picks the scene builder), so the per-card look stays CSS and contexts never multiply per card: **Card Skins** gets `three/skinShopFx.js` ("atelier" — ghost "24" cards tumbling down a gold glitter curtain, rarity bokeh, glint flares, light sweep), **Boost Items** and **Inventory** get `three/itemFx.js` ("vault" — rising gold/amber motes, spinning halo ring). All scenes are built on the skinScenes primitives and follow the GameBackdrop discipline (dynamic import, qualityGuard, IntersectionObserver skip for hidden v-show tabs, full dispose).

### API surface

- `GET /api/v1/items` — public catalog + (with token) `owned` map (`{itemId: qty}`) and `active` map (item id → `endsAt` RFC3339 for the window running now, matched on kind + multiplier).
- `POST /api/v1/items/{id}/buy` with optional `{count}` (default 1, integer 1–200) — 200 `{player, count}`; the batch debits price×count at once; errors: 403 guest, 400 invalid count / insufficient coins, 404 unknown item.
- `POST /api/v1/items/{id}/use` with optional `{count}` (default 1, integer 1–200) — 200 `{player, boost, action, replaced, count, capped}` (`action` = `fresh` | `extended` | `replaced`, `capped` = the window end was trimmed at 24h); errors: 403 guest, 400 invalid count / no (or not enough) items left / "boost duration cap exceeded (24h)" (`store.ErrBoostDurationCap`, nothing consumed) / "time items extend the round timer and are used in game" (kind `time`) / "skip items are spent by the in-game Skip button" (kind `skip`), 404 unknown item.
- `POST /api/v1/rounds/{id}/extend` — spends one time item on an open solo round, any time mid-play: 200 `{roundId, timeLimit, extraSeconds, player}` (`extraSeconds` is the clamped value actually granted); errors: 403 guest (`ErrGoogleRequired`), 400 no time item in inventory (`ErrNoItems`) / "time extension already used this session" (`ErrSessionExtendUsed`) / "round time is already at this mode's limit" (`ErrRoundTimeFull`, nothing consumed), 404 unknown round/item, 409 round already finished (`ErrRoundClosed`).
- `POST /api/v1/rounds/{id}/skip` — spends one skip item to fold an open solo round: 200 `{solution, newAchievements, player}`; errors: 403 guest (`ErrGoogleRequired`), 400 no skip item in inventory (`ErrNoItems`) / "skip already used this session" (`ErrSessionSkipUsed`), 404 unknown round, 409 round already finished (`ErrRoundClosed`).
- `POST /api/v1/rounds/{id}/timeout` — the free fold for a hand whose window genuinely ran out (expiry verified server-side, extension + 10s grace included): 200 `{solution, newAchievements, player}`; errors: 400 "time not up yet", 404 unknown round, 409 round already finished.

## Admin economy management

The admin portal (ADMIN_EMAILS allowlist, `internal/handler/admin.go`) can correct a player's meta-game economy directly; every mutation is event-logged with the acting admin as actor. Every player-facing mutation also pushes a fresh profile snapshot through the player's live socket (see Live profile socket), so open tabs update without a refresh.

- **Coins**: `POST /api/v1/admin/players/{id}/coins` with `{value}` — overwrites the balance outright (the admin UI pre-fills the current value); negatives → 400, unknown player → 404 (`store.SetPlayerCoins`, event `admin.coins.set` with the before/after pair). The admin player JSON (list + detail) carries `totalCoins`.
- **Achievements**: `POST /api/v1/admin/players/{id}/achievements/grant` and `.../revoke` with `{id}` (`store.GrantAchievement` / `store.RevokeAchievement`, events `admin.achievement.grant` / `admin.achievement.revoke`). Granting pays the entry's standard EXP/coin rewards onto the lifetime totals only (never per-mode stats), exactly like a natural unlock; a double grant → 409, unknown achievement/player → 404. Revoking removes only the unlock row — banked rewards stay, and a revoked entry re-unlocks on the player's next evaluation if its condition still holds. Admin adjustments deliberately do **not** trigger an evaluation cascade (evaluation points stay as listed under Achievements).
- **EXP**: `POST /api/v1/admin/players/{id}/exp` with `{mode, value}` — overwrites that mode's EXP with an absolute value (negatives → 400) and resyncs `total_exp` to the per-mode sum (`store.SetPlayerEXP`, event `admin.exp.set`).
- **Tier**: `POST /api/v1/admin/players/{id}/tier` with `{tier}` — stores a tier override on `players.tier` (`store.SetPlayerTier`, event `admin.tier.set`); `{tier: ""}` clears it. Tiers are bronze → silver → gold → platinum → diamond → master (`progress.TierFromName` validates; unknown names → 400). The override replaces the level-derived tier **everywhere**: profile JSON, single-player and admin leaderboards, room seats (websocket join) and the tier hint bonus (`progress.TierBonusQuota`). `players.tier` empty string = derive from level, the normal path.
- **Ban/unban**: `PATCH /api/v1/admin/players/{id}` with `{banned, banReason}` (`store.SetPlayerBanned`, events `admin.ban` / `admin.unban`). An admin can never ban their own account — the API refuses with 400 (`cannot ban your own admin account`) and the portal hides the button on self rows. Banning pushes a terminal `banned` event through the player's live socket (reason included) instead of the plain profile snapshot; unbanning resumes normal pushes and the player's old token works again immediately.
- `GET /api/v1/admin/players/{id}` detail now also returns `achievements` — the player's unlocked entries (id, tier, title, rewards, unlock timestamp RFC3339), newest first.

### Database settings: backup & restore

- **Backup**: `GET /api/v1/admin/db/backup` streams a consistent `VACUUM INTO` snapshot as a download. Resets and restores always write a safety snapshot `game24-backup-<timestamp>.db` next to the database first (same-second collisions grow a `-N` suffix); `GET /api/v1/admin/db/backups` lists those server-side files (name, size, modified) for the Settings page.
- **Restore**: `POST /api/v1/admin/db/restore` (`store.RestoreFrom`) replaces the live data with a snapshot — either `{"name": "game24-backup-…db", "confirm": "RESTORE"}` for a server-side file (name must match `game24-backup-*.db`, so no path traversal) or a multipart upload (`file` + `confirm=RESTORE`, staged to a temp file that is removed with the request; 1 GiB cap). Validation runs before anything is touched: readable SQLite image, the four core tables present, and a decrypt probe on one nickname — a snapshot written under a different `ENCRYPTION_KEY` → 400 (`store.ErrInvalidBackup`). All rows then move in one transaction (only columns shared by both schemas are copied, so older snapshots tolerate newer columns); on failure the live data is untouched.
- **Consequences**: sessions recorded inside the snapshot come back to life; every token minted after it dies — usually including the acting admin's. The restored event log gains one `db.restore` entry recording the actor, the restored file and the safety file. The Settings UI (English-only, like the whole portal) lists server-side snapshots with per-row Restore, accepts uploads, and requires typing RESTORE — mirroring the reset flow.

## Live profile socket

- `/api/v1/ws/player` (`internal/handler/wsplayer.go`) is a per-player **websocket** that keeps every open tab of a player in sync without a page refresh. One tab = one socket, multiple tabs each hold one; the Vite dev proxy already forwards it (`ws: true` on `/api`).
- **Protocol** mirrors the room socket's `{type, data}` envelope: the first client message must be `{"type":"auth","data":{"token":...}}` (token in the payload, never in the URL) within 10s or the socket is closed; an unknown/dead/banned token gets one `error` message then a close. After auth the server sends a full `player` snapshot (`{"type":"player","data":{"player":<player JSON>}}`), then relays presence pushes live: `player` events carry a complete fresh profile, `banned` (`{"reason"}`) announces a fresh ban, `deleted` announces the account is gone — the client drops the dead session in both cases — and `boost` (`{"boosts": {…}}`, the full active view) announces a server-wide boost change.
- **Publish points** (`api.notifyPlayer` / `api.notifyPlayerBanned` / `api.notifyPlayerDeleted` in `internal/handler/notify.go`, nil-broker tolerant): every admin player mutation (coins, EXP, tier, grant/revoke, rename, stat reset) pushes `player`; a fresh ban pushes `banned`; deletes push `deleted`; plus self-service rename, delete from another tab, and item buy/use (inventory counts + personal boost icons). Solo hand payouts don't publish — their REST responses already carry the fresh profile inline.
- **Transport discipline**: fan-out goes through `internal/presence`; delivery is best-effort and never blocks the mutating handler — a socket whose buffer (16) overflows is kicked and left to resync through reconnect. Timings and origin policy mirror the room socket (10s write deadline, 60s pong wait, 45s ping period, shared `ws.CheckOrigin`).
- **Client** (`web/src/realtime.js`, wired once from `main.js`): applies `player` events to the reactive `currentPlayer` ref (bumping `playerIdentityVersion` on renames), acts on `banned`/`deleted` by raising the global ban dialog (`BannedModal.vue`, mounted from `App.vue`; state lives in `auth.js` as `banNotice`/`markBanned`) and signing out, and reconnects with full-jitter exponential backoff hard-capped at 30s. The backoff resets **only after a socket has stayed up ≥10s** — a socket that dies instantly must never loop at full speed (that once hammered the endpoint and tripped the shared 200 req/min rate limit). Reconnects eagerly on `online`/visibility regain. Every ban encounter surfaces through that same dialog: a live `banned` push; a reconnect auth rejected with `error` `"account banned"`; a `restoreSession` against a banned token; and a sign-in attempt — `POST /auth/google` 403s with the same message and `signInWithGoogle` raises the dialog instead of an inline error line.

## Account deletion

- Players delete their own account through `DELETE /api/v1/me` (`store.DeleteOwnPlayer`), **Google accounts only** — guests are rejected with 403 (`google sign-in required`, same gate style as the skins endpoints). The body must confirm with `{"confirm":"DELETE"}` — the exact word, mirroring the admin DB reset guard; anything else → 400.
- Deletion is a **hard delete**: the `players` row goes and every dependent table cascades (`player_mode_stats`, `rounds`, `player_achievements`, `player_skins`, `player_items`, `player_boosts`), so profile, EXP/level, coins, achievements, owned skins, item inventory and full round history all vanish irrecoverably. The session token dies with the row — the next authenticated call 401s.
- The audit trail distinguishes paths: self-service logs `player.delete` with actor `player:<id>`, the admin portal keeps `admin.delete` (shared helper `store.deletePlayer`).
- UI entry: the profile menu's danger item → `DeleteAccountModal.vue`, which warns that everything is permanently erased and unrecoverable and requires typing DELETE; the modal links to `/privacy`. On success the client clears the session and re-opens the entry flow.
- **Guest profile menu** (`ProfileMenu.vue`): guests get a reduced menu — only rename plus a Google sign-in row with the `guestMenuHint` nudge. The achievements and skins links and the delete action are hidden (`isGuest` gate), mirroring the server gates.
- The legal copy describes the self-service deletion: Privacy Policy ("Retention & deletion") and Terms ("Player accounts") in `web/src/i18n/legal.js` — bump `OPERATOR.updated` when touching legal copy.

## Card Skins

- Catalog of **12 card skins** in `internal/skins` (`skins.Catalog`): `classic` (free default) up to `inferno` (6500 coins). Rarity bands: common / rare / epic / legend.
- **Google-gated**: buying and equipping require a non-guest player (`store.ErrGoogleRequired` → HTTP 403). Guests see the shop but cannot purchase or equip; the UI shows the Google sign-in gate.
- A skin is a **visual theme plus a signature animation stack** — per-skin custom properties (`--skin-face`, `--skin-ink`, `--skin-red`, `--skin-border`, `--skin-glow` for the selection ring) scoped by a `.skin-<id>` class on the game board; `CardTile.vue` consumes them with classic-looking fallbacks. Premium skins layer three levels of effects:
  - **CSS ambience** (neon flicker, gold sheen sweep, sakura petals, …) in `web/src/skins.css`, mirrored on the shop's `.pcard` previews.
  - **A pointer-tracked holographic foil** — a real `.holo` element inside every card/preview whose gradients follow the cursor through the registered `--mx`/`--my` custom props (per-skin foil backgrounds in `skins.css`; classic/mono keep it at opacity 0). Follow-the-pointer only runs for fine pointers without reduced motion; everyone else sees the static sheen.
  - **A three.js scene pair** (`web/src/three/skinScenes.js`, mounted by `SkinFx.vue`) with **two canvases**: an ambience scene behind the cards (one GPU-shader scene per skin — galaxy spiral disc with differential rotation, inferno ember storm (drifting sparks over a breathing molten glow), midnight aurora + moon, ocean god rays, neon synthwave grid with scheduled glitch tears, …, all with damped pointer parallax) and a **celebration scene above the cards**: `GameBoard` calls `SkinFx.burst(x, y, strength)` at every card merge (`strength 1` when the merge makes 24), firing the skin's shockwave ring + core flash + spark shower over the board.
  - The mobile profile sheet's golden particle halo (`three/profileHalo.js` + `ProfileHalo.vue`) follows the same GameBackdrop discipline (dynamic import, qualityGuard, hidden-tab pause, full dispose); its layout math (`ringPositions` / `sparkField` / `advanceSparks`) is pure and pinned by `three/profileHalo.test.mjs`.
  - The shop intentionally stays CSS-only (a WebGL context per preview would blow the browser's context limit). No gameplay effect; all motion is gated behind `prefers-reduced-motion` (bursts included), and the three.js layers follow the `GameBackdrop` discipline (dynamic import, qualityGuard, hidden-tab pause, full dispose). Scene layout math (`spiralLayout`, `circleLayout`, `glintCurve`, `burstFade`) is pure and pinned by `web/src/three/skinScenes.test.mjs`.
- Buying debits `players.total_coins` in one transaction with the ownership insert; equipping writes `players.skin` and requires prior ownership. `classic` is always equippable and never purchasable.
